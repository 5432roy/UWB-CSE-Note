- Every machine should keep information about the number of vertices, nodes, processors (machines), and the division. *The exact meaning of “division” and the relationship between these items are unclear in lecture.*
- **Each machine keeps its partial adjacency list in its own memory.**

## Loop parallelism

**Loop parallelism** parallelizes computation within a loop to improve performance.

The main challenges are:

- Allocating chunks of iterations to different processors.
- Maintaining data dependencies across iterations.

## Matrix multiplication: Multi-process and multi-threaded solutions

Both solutions divide the matrix computation by rows. Each worker reads its assigned row `a[i][]` and the shared matrix `b[][]`, then writes the corresponding output row `c[i][]`.

### Memory layouts

| Feature | Multi-process solution | Multi-threaded solution |
| --- | --- | --- |
| Workers | A parent process and three child processes created with `fork()`. | A main thread and three child threads within one process. |
| Address space | Each process has its own address space, with code, an ordinary heap, and a stack. | All threads share one process address space, including its code and heap. |
| Matrix storage | `shmget()` obtains shared-memory segments for the matrices, and `shmat()` maps them into the process address spaces. | The matrices are stored in the shared heap and are accessible to all threads. |
| Stacks | Each process has its own stack. | Each thread has its own stack. |
| Work assignment | Each process handles one input row and the matching output row in the diagram. | Each thread handles one input row and the matching output row in the diagram. |

In both diagrams, the four workers handle rows `0`, `1`, `2`, and `3`. All workers read `b[][]`. The highlighted rows show which part of the computation each worker handles; the matrices remain shared.

**Threads share the matrix storage directly through the process's heap**, so the multi-threaded solution does not need the explicit shared-memory attachment operations shown in the multi-process solution. Assigning different output rows still requires loop partitioning, and workers must synchronize when the program needs all results to be complete.

## Multi-process problems — Shared Memory 1

A multi-process parallel program must manage shared memory, create and terminate processes, partition loop iterations, and synchronize workers.

### Shared memory and process functions

| Function | Purpose | Role in a parallel program |
| --- | --- | --- |
| `shmget()` | Creates or finds a System V shared-memory segment and returns its integer identifier. | Obtains the shared storage that processes will use. |
| `shmat()` | Attaches the segment to the calling process's address space and returns a pointer to it. | Lets the process read and write the shared data through that pointer. |
| `shmdt()` | Detaches the segment from the calling process's address space. | Releases that process's attachment when it finishes using the shared data. |
| `fork()` | Creates a child process. It returns the child's PID to the parent, `0` to the child, and `-1` on failure. | Creates workers; the return value lets parent and child follow different code paths. |
| `exit()` | Terminates the calling process and supplies an exit status. | Ends a worker after its assigned computation. |
| `wait()` | Waits for a child to terminate and collects its status. | Lets a parent wait for a worker to finish. Each successful call collects one child's status. |
| `semop()` | Performs operations on System V semaphores, potentially blocking until an operation can proceed. | Coordinates access to shared data or signals that work may proceed. |

**`shmget()` returns an identifier; `shmat()` returns a usable memory address.** Processes can access the same segment even if it is attached at different virtual addresses. See the documentation for [shmget](https://man7.org/linux/man-pages/man2/shmget.2.html) and [shmat/shmdt](https://man7.org/linux/man-pages/man2/shmat.2.html).

Process-function references: [fork](https://man7.org/linux/man-pages/man2/fork.2.html), [exit](https://man7.org/linux/man-pages/man3/exit.3.html), [wait](https://man7.org/linux/man-pages/man2/waitpid.2.html), and [semop](https://man7.org/linux/man-pages/man2/semop.2.html).

### Loop partition and synchronization

**Loop partitioning** assigns each worker a range of iterations by calculating its first and last iterations using process IDs. *The slide does not show the calculation or establish whether these IDs are OS PIDs or assigned worker indices.*

The slide lists two levels of synchronization:

- **OS level:** `wait()` and `semop()` coordinate processes through operating-system facilities.
- **User level:** a barrier is implemented with a shared variable. A **barrier** makes workers wait until all participating workers reach the same point before continuing.
